# 模块 12 应用监控 —— 验收与演示手册

> 目标：用 **Apifox 自动化测试** 证明「接口行为正确」，用 **JUnit 测试类** 证明「打点逻辑与配置正确」。
> 演示只讲 5 个点，其余一键跑过即可。

---

## 0. 一句话说清两条线的分工

| 工具 | 验的是 | 证明力 | 演示价值 |
|---|---|---|---|
| **Apifox 自动化测试** | 跑起来的应用对外表现 | 真实 HTTP、真实指标累积、真实导出格式 | 评委能自己点着看，最有说服力 |
| **JUnit 测试类** | 类里面的逻辑 | 不起 Spring 也能测打点；起 Spring 能测端点 | 证明「不是碰巧对了」，改坏了会红 |

两条线都过 = 代码对。只有一条过 = 多半是环境问题（见文末排查）。

## 2. Apifox 自动化测试：一条命令跑完全部断言

### 怎么跑

1. 左侧目录选中「**12-actuator 应用监控验收**」
2. 右上角 **自动化测试 → 创建测试场景 → 引用当前目录**
3. 确认执行顺序就是 01 → 11（**顺序不能乱**，见下面「为什么有顺序」）
4. 选环境「12-actuator 本地」→ **运行** → 报告里 30 条断言应该全绿

### 11 条接口各自验什么

| # | 接口 | 关键断言 | 讲不讲 |
|---|---|---|---|
| 01 | `GET /actuator/health` | `components.inventory.status=UP` 且带 `url`/`latencyMs` | **讲**（见 §4.1） |
| 02 | `POST /business/orders` | 200 + `orderId`/`costMs` | 略过 |
| 03 | `GET /business/slow?ms=300` | `responseTime >= 300` | 略过（它存在的意义是给 07 提供大样本） |
| 04 | `GET /business/fail?reason=stock_empty` | 200 + reason 回显 | 略过 |
| 05 | `GET /actuator/metrics` | 四个自定义指标都在 + `http.server.requests` 在 | 略过 |
| 06 | `GET /actuator/metrics/business.orders.created` | 只有 `COUNT`、值 >0、带 `application` 标签 | 略过 |
| 07 | `GET /actuator/metrics/business.order.handle?tag=result:success` | COUNT/TOTAL_TIME/MAX 齐全，**MAX ≥ 0.25s** | **讲**（见 §4.2） |
| 08 | `GET /actuator/metrics/business.orders.processing` | `VALUE = 0` | **讲**（见 §4.3） |
| 09 | `GET /actuator/prometheus` | 见 §4.4 四条 | **讲**（重点） |
| 10 | `GET /actuator/env` | **404** | **讲**（见 §4.5） |
| 11 | `GET /actuator/info` | `module`/`owner` + `app.version` | 略过 |

### 为什么有顺序

`business.orders.failed` 是 **懒注册** 的：没打过一次失败点，它压根不在注册表里。
所以 05 的「四个指标都在」依赖 04 先跑过。演示时如果有人问「指标清单为什么少一条」，答案就是这个——不要以为是配置没生效。

## 3. JUnit 测试类：两层，分开讲

```bash
# 全部一起跑（16 个用例）
mvn -pl 12-actuator test

# 只跑某一个类
mvn -pl 12-actuator test -Dtest=BusinessMetricsTest
```

| 测试类 | 用例数 | 层次 | 演示时怎么讲 |
|---|---|---|---|
| `BusinessMetricsTest` | 5 | 纯单元，**不起 Spring** | 「打点对不对，不需要启动应用就能证明」 |
| `InventoryHealthIndicatorTest` | 2 | 纯单元 | 「UP/DOWN 两个分支，`ReflectionTestUtils` 塞字段」 |
| `AppInfoContributorTest` | 1 | 纯单元 | 「`MockEnvironment` 比 Mockito 省一堆 `when`」 |
| `ActuatorEndpointTest` | 8 | 集成，`@SpringBootTest` + MockMvc | 「端点真的挂上了、真的能访问、真的能 404」 |

### 只演示 3 个方法（其余点开看一眼结果就行）

**① `BusinessMetricsTest.gaugeTracksProcessing`** —— 为什么 Gauge 要在测试里才看得见

```java
Gauge gauge = registry.get("business.orders.processing").gauge();
assertThat(gauge.value()).isZero();
metrics.enter(); metrics.enter();
assertThat(gauge.value()).isEqualTo(2.0);   // 同一时刻读，才读得到
```

一句话：**测试里 enter 之后立刻读，所以能看到 2；线上 curl 时请求早结束了，所以永远是 0。** 两处口径对上，这个「0」就不再是 bug。

**② `ActuatorEndpointTest.counterGrowsByThree`** —— 为什么断言的是差值不是绝对值

```java
double before = registry.get("business.orders.created").counter().count();
for (int i = 0; i < 3; i++) mockMvc.perform(post("/business/orders"));
double after = registry.get("business.orders.created").counter().count();
assertThat(after - before).isEqualTo(3.0);
```

一句话：**容器里 registry 是单例，别的用例也会打点，写 `isEqualTo(3.0)` 换个执行顺序就红。** 这条能体现「测试写过」，不是抄的。

**③ `ActuatorEndpointTest.unexposedEndpointIs404`** —— 安全面也有测试兜着

```java
mockMvc.perform(get("/actuator/env")).andExpect(status().isNotFound());
```

一句话：**哪天有人为了「方便排查」把 `exposure.include` 改成 `*`，这条会红。** 这是把安全约定写进测试。

## 4. 五个必讲的点（照着说就行）

### 4.1 自定义健康检查进的是组件树，不是旁支

Apifox 01 的返回里直接能看到：

```json
"inventory": {
  "status": "UP",
  "details": { "url": "http://inventory-service/health", "latencyMs": 0, "checkedAt": ... }
}
```

讲法：`@Component("inventory")` 这个 Bean 名就是响应里的 key。`Health.up().withDetail(...)` 带的 `url`/`latencyMs` 是给人排查用的——只报 UP/DOWN 只能说「坏了」，带上依据才能说「坏在哪」。

**现场加一个演示（可选，30 秒）**：改 IDEA 的 VM options 或命令行加 `--demo.inventory.healthy=false` 重启，再请求：

```bash
curl -i --noproxy '*' http://127.0.0.1:8012/actuator/health
```

关键在状态码：**HTTP 503**，body 里 `status: DOWN`、`inventory.details.reason: 连接超时`。
讲法：健康检查不是给人看的页面，是给负载均衡和 k8s 探针用的——**503 才是能被自动摘流的信号**，返回 200 带个 DOWN 字样等于没检查。

### 4.2 P95 从哪来的：慢请求 + MAX + quantile

先跑 03 三次（`ms=300`），再请求 07。

```json
"measurements": [
  { "statistic": "COUNT",      "value": 5.0 },
  { "statistic": "TOTAL_TIME", "value": 0.905 },
  { "statistic": "MAX",        "value": 0.303 }
]
```

讲法：3600 次快请求 + 3 次 300ms 慢请求，平均值（`TOTAL_TIME / COUNT`）根本看不出来，**P95 才看得见尾巴**。这就是为什么监控看分位数不看平均值。

再补一句最容易踩的：**Micrometer 的百分位是 1 分钟滚动窗口**（3 个桶 × 20 秒）。刚才那个慢请求过 1 分钟就滚出去了，P95 会跳回 0——不是数据坏了，是窗口滑走了。`_count` / `_sum` 是累计的，不会消失。

### 4.3 `processing` 永远是 0：口径问题，不是 bug

Apifox 08 断言的就是 `VALUE = 0`。

讲法：Gauge 只在**被抓取的那一刻**读当前值。`enter()` 和 `leave()` 之间只隔几微秒，你 curl 的时候请求早结束了。
对照 `BusinessMetricsTest.gaugeTracksProcessing`——测试里 enter 之后立刻读，读到的是 2。**两次读数差的是时间，不是逻辑。**

延伸一句（有加分）：这类「太快看不到」的 Gauge 实践意义有限，真正有用的是队列长度、连接池占用这种会持续存在的量。

### 4.4 名字为什么和代码里写的不一样（重点）

代码里写 `business.orders.created`，Apifox 09 的断言和实际导出是：

```text
# TYPE business_orders_total counter
business_orders_total{application="12-应用监控"} 3.0
```

讲法：Prometheus 的命名约定是**下划线分隔 + 单调计数器以 `_total` 结尾**。Micrometer 自动做两件事：
1. 点号 → 下划线
2. 见到 `created` 这类「保留后缀」直接吃掉，再补 `_total`

**所以业务名里别用 `count` / `total` / `created` 这类词**，否则导出名会和你想的不一样，Grafana 面板上的查询也就跟着错。

同一个导出里还能看到 Timer 的下场：

```text
# TYPE business_order_handle_seconds summary
business_order_handle_seconds{...,result="success",quantile="0.95"} 0.301989888
business_order_handle_seconds_count{...,result="success"} 4
business_order_handle_seconds_sum{...,result="success"} 0.302
```

讲法：**分位数不是独立指标，是 quantile 标签**；`_count`/`_sum` 才是能长期聚合的两个数。想接 Grafana 算真正的全量 P95，应该开 `percentiles-histogram` 走 `_bucket`，而不是依赖 summary 的滚动 quantile。

### 4.5 为什么 `env` 必须 404

Apifox 10 断言 404，同一脚本里还 sendRequest 了 `/actuator/metrics` 断言 200 做对照。

讲法：`/actuator/env` 能读出全部配置（数据库密码、第三方 AK/SK 全在里面），`/beans`、`/configprops` 同理。所以：
- 默认只暴露 `health`
- `exposure.include` 白名单逐个开，**永远不要写 `*`**
- 这条 404 由 `ActuatorEndpointTest.unexposedEndpointIs404` 守着，谁改了会红

顺带一个 Boot 4 的坑（现场讲很值）：`management.info.env.enabled` 在 Boot 4 里**默认变成了 false**（Boot 3 是 true）。不显式打开，`application.yml` 里那段 `info.app` 根本不会出现在 `/actuator/info`——这个是我实际跑的时候才发现的，已经在 `application.yml` 里显式打开，并且加了测试 `infoHasStaticConfigFromYml` 盯着。

## 6. 现场翻车排查

| 现象 | 原因 | 处理 |
|---|---|---|
| Apifox 全部 `ECONNREFUSED` | 应用没起 / 端口不对 | `curl --noproxy '*' http://127.0.0.1:8012/actuator/health` 先确认 |
| Apifox 里 `/actuator/health` 显示不全 | 客户端没有走 `show-details` 的效果？不是 | 检查 `management.endpoint.health.show-details: always` 有没有被 IDEA 的 override 覆盖 |
| 05「四个指标都在」红 | 04 没先跑（懒注册） | 按 01→11 顺序跑 |
| 07 `MAX >= 0.25` 红 | 03 没跑或跑太少 | 先跑 03 三次 |
| 09 找不到 `business_orders_total` | 02 没跑过 / 名字又被改了 | 先跑 02，再核对 `BusinessMetrics` 里的指标名 |
| 11 的 `app.version` 红 | `management.info.env.enabled` 被注释了 | 检查 `application.yml` 第 20 行附近 |
| `mvn test` 报端口占用 | 应用正在 8012 上跑 | MockMvc 走 MOCK 模式本不占端口，占端口的是别的进程；`netstat -ano \| grep :8012` 查 |
